# 利用しやすさ改善計画

更新日：2026-11-13
状態：進行中
基準仕様：[仕様書](specification.md) 0.12

## 目標

高校生が「身近な困りごとを選ぶ → データまたは自分の画像を用意する → CV機能を実行する → 結果を見て次の行動を考える」までを、環境設定や形式変換に迷わず進められる状態にする。

簡潔なAPIを保ちつつ、データの出典・ライセンス・注意点、モデルの得意不得意、結果の意味は隠さない。依存を勝手にインストールしたり、GPUへ自動切り替えしたりしない。

## 現状

- インストールは機能別extraに分かれている。PyTorchはCPU/GPU用を先に選び、OCRはPaddlePaddleも別導入する。説明が機能ごとに分散していて、最初に選ぶ環境や最短導線が分かりづらい。
- データは`datasets.list_tasks()`で課題から探し、`datasets.get()`で取得できる。`DatasetBundle.to_df()`は分類、検出、領域分割、回帰、OCRで列が異なる。`to_torch_dataset()`は分類と領域分割に対応し、検出・OCR・回帰は別の入力形を使う。
- モデル画像入力は、ファイルパスに加えてPillow Imageへ対応。データセットの画像はパスのまま使え、手元画像はメモリ上の画像を渡せる。共通表示APIで検出・OCR・SAM結果を重ねて表示・保存できる。NumPy画像配列は共通入力対象外。Colabへの自分の画像アップロード例が不足しているため追加する。
- 機能ごとのAPIと個別説明はあるが、「どのデータをどう選び、どのモデルへ渡し、結果をどう見るか」を一連で試す手順は揃っていない。
- ColabでOCR CPUとDETR・SAM T4の実モデル推論を確認済み。導入・検出ガイドの記述は実測状態に更新済み。Colabでの共通表示APIの動作と日本語フォント表示は未確認。

## 改善順

### 1. 入口と導入方法を整理する

1. PyPI公開前のGit固定版導入と、PyPI公開後の通常導入を区別する。
2. CPUローカル、Colab CPU、Colab T4、OCR専用環境ごとに、導入順・コマンド・必要な追加パッケージ・モデル容量・GPU選択方法を1か所にまとめる。
3. 初心者向けの最短導線を用意し、「データ閲覧だけ」「ResNet」「OCR」「検出・領域分割」「SDXL」のどれに何を入れるかを選べるようにする。
4. `all` extraや実行時の自動pip installは導入しない。PyTorch/PaddlePaddleの環境別wheel選択と依存分離を維持する。

完了条件：利用者が目的の機能に必要な導入だけを選べる。対応Python、CPU/GPU条件、実測済み環境、未確認環境が同じ表と最短手順に示される。Colabでの依存導入後にカーネル再起動が必要な場合は、再開位置が明記される。

### 2. データを選んで、すぐ中身を確認できるようにする

1. 課題一覧から、タスク、件数、ダウンロード量、形式、split、ライセンス、出典、注意点までを一続きで見られるようにする。
2. `get()`後に、件数・クラス・分割・サンプル画像・ラベルまたは注釈を簡単に確認する導線を整える。
3. データ形式をタスク別に保ちながら、画像パス、ラベル、split、sample ID、注釈の取得方法と列名を共通の案内表にする。
4. `DatasetBundle`からモデルへ渡すまでの手作業を棚卸しする。分類・回帰の`X/y`、検出bbox、領域マスク、OCR画像と正解見本について、実装済みの変換と不足を分ける。
5. 必要な便利APIが現在の仕様で決めきれない場合は、実装前に仕様書へ契約を追加する。元データやsplit、注釈は保持し、利用のための表現変換は別ビューとして扱う。

完了条件：掲載済みデータすべてについて「取得 → 内容確認 → タスクに合う形式で参照」のサンプルがある。未対応タスクのデータを、対応済みの学習形式であるかのように見せない。

### 3. 画像入力と結果の見方を揃える

1. ファイルパス、Pillow画像、必要に応じてNumPy配列、データセットの画像レコードを各機能がどう受け取れるかを比較する。
2. 初心者向けの入力方法を決め、パス変換や一時ファイル作成を利用者に繰り返し要求しない形を設計する。ファイルパス対応は維持する。
3. OCR文字枠、検出bboxラベル、SAMマスクの半透明重ね合わせを共通の表示・保存方法で確認できるようにする。
4. 結果はタスクごとの有用な値を維持し、必要な場合に標準Python型へ変換できるようにする。SAMの品質予測値のように、確率や実測値ではない指標の意味も表示する。
5. CPU/GPU、モデル初回取得、キャッシュ利用、画像の寸法制限や戻り値型を最小例で示す。

完了条件：同じ画像入力の扱いを各機能の例で学べる。検出・OCR・領域分割の結果を追加の自作描画コードなしで画像とともに確認・保存できる。結果の数値が何を示すか説明される。

### 4. 課題から完成例までをつなぐ

1. 入口となる短いColab Notebookを用意し、データを使う例と手元画像を使う例を分ける。
2. 分類学習、回帰、OCR、検出、領域分割、画像生成から、機能ごとにオーソドックスな1例を選ぶ。
3. 各例を「困りごと・入力・数行の実行コード・結果の見方・次に変えられる点」で統一する。
4. 実装済み機能・Colabで実測した機能・未確認の機能を分けて示す。モデル能力の例は、唯一の用途のように制限しない。
5. Notebookの見出しや授業の順序を変える必要がある場合は既存Notebookを改変せず、別の補助Notebookとして追加する。

完了条件：各主要タスクで、初心者が画像・データの選択から結果確認まで実行できる。GPUが必要な例は対応ランタイムを事前に選べる。

### 5. 一貫性と再現性を検証する

1. インストールコマンド、実際のextra、README、APIリファレンス、Notebookの固定commitを照合する。
2. データ取得、モデルの遅延取得、キャッシュ位置、結果型をネットワーク不要テストで検査する。
3. 各主要ユーザーフローを新規環境とColabで1回ずつ確認する。全OSと全GPU構成を総当たりしない。
4. 実測したPython・依存版・CPU/GPU・モデルrevision・実行結果を記録する。
5. 仕様の受け入れ条件と異なるAPI案が出た場合、コードより先に仕様書を更新する。

完了条件：新規環境での導入から出力確認まで再現でき、失敗時に足りない依存・必要な再起動・取得対象が分かる。テスト結果は実環境確認や公開完了と混同しない。

## 実装上の境界

- データやモデルのライセンス、取得先、固定revision、キャッシュの安全性を簡略化しない。
- インストールをライブラリが自動実行しない。GPUを自動選択しない。
- 巨大な依存を基本installへまとめない。OCRとPyTorch系の同一環境利用を前提にしない。
- 今回はタスクの種類、学習可能範囲、採用データ・LoRAの件数を増やすことを目的にしない。
- 使いやすさのためにタスク別の正解ラベル、分割、マスクやbboxの意味を壊さない。
